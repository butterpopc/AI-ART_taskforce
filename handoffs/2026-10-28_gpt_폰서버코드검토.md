## 1. 로그인 우회

## 3. 요청 위조

- [심각도: 중간] server.py:301,319 — 로그인에는 요청 출처 검사가 없어 외부 사이트의 폼 POST를 처리한다.
  재현: 다른 Origin과 application/x-www-form-urlencoded 형식으로 /login에 시험 비밀번호를 보내면 303과 새 세션 쿠키가 반환된다. 비밀번호를 모르는 사이트도 잘못된 값으로 잠금 횟수를 소모할 수 있다. 로그인 전에는 보호할 기존 쿠키가 필요 없으므로 SameSite=Strict만으로 막히지 않는다. 세션 탈취나 비밀번호 우회가 확인된 것은 아니다.
  확인 수준: 실측(HTTP 서버가 외부 Origin 요청을 수락함). 실제 Chrome에서 외부 폼·쿠키 반영·로컬 네트워크 접근 허용 여부는 미실측.

RPC: 이상 없음 (확인 수준: 코드 검토 + HTTP 실측). 인증 쿠키가 있어도 X-NSL 없으면 403. OPTIONS 사전 요청은 501이며 CORS 허용 헤더가 없다. 일반적인 다른 출처 페이지는 필요한 헤더를 붙여 호출할 수 없다.

## 4. 비밀번호·세션

## 7. 동시 실행·저장

- [심각도: 중간] web/js/api.js:43, app/bridge.py:172 — 클라이언트별 draft 순번을 서버 전체에서 하나로 비교해 새 탭·새로고침의 임시 입력을 버린다.
  재현: 첫 클라이언트에서 seq=30으로 draft를 보낸 다음 새 클라이언트에서 seq=1로 다른 draft를 보내고 종료한다. 새 값은 무시되고 첫 draft 값이 저장됐다. 명시적인 설정 저장 요청과는 별개인 종료 시 임시 입력 보존 결함이다.
  확인 수준: 실측(ServerApp 호출과 shutdown). 브라우저에서 순번이 초기화되는 점은 api.js 대조.

- [심각도: 중간] server.py:355, main.py:159 — 서버와 PC 앱 사이 중복 실행 방지가 한 방향뿐이며 Windows에서는 기존 서버 PID도 살아 있지 않은 것으로 처리한다.
  재현: Windows에서 같은 data를 쓰는 서버를 먼저 켜고 PC 앱을 켜면 PC 앱은 .server-mode.lock을 확인하지 않는다. 서버 두 개를 다른 포트로 띄울 때도 _pid_alive가 Windows에서 항상 False라 기존 서버 차단이 빠진다. 양쪽 메모리 상태가 서로 다른 채 저장해 덮어쓸 수 있다. 폰 기본 실행에 그대로 해당하는 Windows 문제는 아니다.
  확인 수준: 추정(코드만 읽음). Windows 미실행. 추가로 잠금 파일 확인과 생성이 원자적이지 않아 POSIX 동시 시작에도 경쟁 여지가 있다.

- [심각도: 중간] server.py:338,443, app/bridge.py:314 — 종료 시 진행 중 요청과 생성 스레드가 끝나기를 기다리지 않아 최종 저장 이후 변경이 생길 수 있다.
  재현: 느린 설정 요청이나 생성 작업 도중 Ctrl+C를 누른다. 데몬 요청 스레드는 server_close에서 대기하지 않고, shutdown도 생성 중단 신호와 저장만 수행한다. 저장 이후 요청이 진행되거나 프로세스 종료로 진행 중 작업이 잘려 마지막 변경·생성 결과가 빠질 수 있다.
  확인 수준: 추정(코드만 읽음). 실제 Ctrl+C 타이밍 재현 및 데이터 손실 실측은 하지 않았다.

엔진의 주요 상태 변경과 저장에 RLock이 있는 것은 확인했다. 위 결과는 모든 요청이 엔진 잠금을 무시한다는 뜻이 아니다.
